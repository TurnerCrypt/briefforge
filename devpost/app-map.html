BRIEFFORGE / REFERENCE MAP

One click. Three places to look.

BriefForge turns explicit instructions into editable checklist items with original source text. This is a reference route through the actual code, not a claim that you have completed a hands-on exercise.

Paste a brief→Find instructions→Render source-backed cards→Save in this browser

1 · The click

app.js — search for $('generate').addEventListener. The button checks that a brief exists, calls the extractor and displays the results.

2 · The rules

extractor.js — extractRequirements looks for explicit instruction patterns. It keeps source separate from editable title. Missing timezones and optional wording become review flags. This is rules-based matching, not model-generated understanding.

3 · The visible result

app.js — render creates the editable text, checkbox, flags and original-source disclosure. Text is inserted using safe DOM text properties, so pasted markup remains text.

Where saving fits

persist in app.js calls saveState in storage.js. That writes the versioned record into browser-local storage. Reopening the same origin loads it with loadState. Clearing browser storage removes it.

To change this, start here

  • Glass tint, blur or button shape: styles.css, .shell, .panel, .forge-button.
  • What counts as a requirement: extractor.js, instruction and extractRequirements.
  • Exported text: extractor.js, toMarkdown.
  • Headings and labels: index.html.

A practice to reuse

Define a checkable outcome before implementing it. Here, “edits survive reopening without changing the original source” connects prd.md > Review and Corrections to separate title/source fields and browser reload verification. On another project, write a similarly visible outcome and check the whole journey, rather than assuming saved data is correct.

Run it again

From the project folder run node server.cjs, then open http://127.0.0.1:4173/. Run core tests with npm test.
